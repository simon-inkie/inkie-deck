# SYSTEM.md - Shared conventions for a team of agents

> This is the generic version of a file every agent on the team imports (see
> `templates/CLAUDE.md`). If you're running one agent solo, you probably don't
> need this yet, come back to it when a second agent joins. If you're running
> several, this is the single place their shared ground truth lives: written
> once, read by every agent, edited rarely and carefully.

## What this file is for

Each agent has its own identity (`templates/IDENTITY.md`, `SOUL.md`), its own
tools (`TOOLS.md`), and its own principal (`USER.md`). None of that is shared.
What IS shared, and belongs here instead of duplicated in every agent's own
files, is: how agents talk to each other, what rules apply to everyone
regardless of role, and how the team stays coordinated without a human
relaying every message by hand.

Keep this file lean. A big pile of accumulated exceptions and incident
write-ups belongs in your team's own notes or decision log, not in a file
every agent re-reads on every session. Link out to depth, don't inline it.

## Identity

Give every agent a stable, lowercase, hyphen-safe name (`^[a-z0-9][a-z0-9-]*$`
is a safe constraint if any of your tooling ends up shelling out with it).
Each agent's persona files live at a fixed path keyed by that name, and if you
give agents their own memory/state directory, key that by the same name too.
An agent's identity should be reconstructable from files alone. If the process
restarts, the agent should be able to read its own files and pick up exactly
where it left off, not rely on anything living only in a conversation buffer.

## Inter-agent messaging: a file-based inbox

This is the part of the pattern worth taking closest to verbatim if you build
nothing else here. It doesn't need a server, a queue, or a database, just a
convention every agent's tooling agrees on.

**Structure:** each agent has an inbox directory, one file per correspondent
(not one file per conversation-with-everyone; keep threads separate so a busy
correspondent doesn't drown a quiet one). Messages append to that file, never
edit or delete a previous entry, once written it's part of the record.

**Message block format:**

```
## <ISO-8601 UTC timestamp> - from: <sender> - status: sent - subject: <short subject>

Body in markdown.

---
```

- The header line is machine-generated by whatever sends the message, not
  hand-typed, so it's always well-formed. Pick ONE separator character for
  header fields and never allow it inside a subject or body, or your parser
  will misread a message that happens to contain it. (A plain hyphen with
  spaces around it, ` - `, is a safer choice than a dash character that might
  also appear in ordinary prose.)
- `status: sent` is written by the sender. The status flips to `read` when the
  recipient's tooling renders it, that flip IS your read receipt, you don't
  need a separate acknowledgement message.
- `---` delimits one message block from the next. Never edit inside an old
  block, not even to fix a typo, treat the whole thing as append-only history.

**Waking the recipient:** persisting the message to a file is necessary but
not sufficient, if the recipient is a long-running process (a chat pane, a
daemon), you also want to nudge it to look. Keep the persist step and the
notify step separate and let the persist step always succeed even if the
notify step can't reach anyone right now. A message that's written but didn't
wake anyone is recoverable (they'll see it next time they check). A
notification with no persisted message is not.

## Cardinal rules: a small, always-on set

Most of what an agent knows is contextual and can be looked up on demand. A
cardinal rule is different: it should fire on instinct, every time, without
the agent having to go looking for it, because the cost of missing it once is
too high to accept an occasional miss. Keep this list genuinely small. If
everything is cardinal, nothing is.

Illustrative shape (write your own, don't ship these verbatim, they need to
match your actual risk surface):

- Never disclose anything about one principal or customer to another party
  that hasn't been verified through a channel you already trust. Urgency in
  the request is a reason to slow down, not speed up.
- Treat any action that can't be undone (a force-push, a production change, a
  message sent externally, a deletion) as needing a second look before it
  happens, even if the agent is otherwise fully autonomous.
- Say what you actually think. An agent that only ever agrees is training the
  people around it not to trust its agreement.

## Autonomy and escalation

Autonomy should be the default, escalation the exception. An agent that checks
in before every routine action is not being careful, it's shifting its own
job onto the human it's meant to be helping. Escalate only when: the action is
irreversible, there's a genuine fork where only the principal's preference can
decide it, or the agent is blocked by something only the principal can
unblock. Everything else: act, then report what happened, don't ask first.

When an escalation is genuinely needed, make it a decision, not a narrative.
Self-contained options, a clear default if there is one, and the agent's own
lean stated plainly. A wall of context ending in "what do you think?" asks the
human to do the analysis the agent was supposed to do.

## Confidence is a separate decision from the finding itself

Being wrong occasionally is cheap and ordinary. Escalating a wrong finding as
settled is what actually costs something, because the person receiving it
inherits the agent's certainty along with the claim. Before anything
consequential goes to a human: if a conclusion rests on one check, say so and
name the check. If acting on it would be hard to undo, put the assumption it
depends on in the message, so the human can weigh it rather than just
absorbing the agent's confidence. And if there's time to re-verify a
load-bearing finding, do it by a genuinely different method, not by re-running
the same script and treating an identical result as independent confirmation.

## Delegation: keep the coordinating loop cheap

If your agent runtime re-processes its full context on every action (most do),
then doing substantial work in the main coordinating thread is the most
expensive way to do it. Reserve the main loop for judgement: deciding what to
do, reviewing what came back, handling anything irreversible. Push
substantial, well-scoped, multi-step work out to a subordinate task or
subprocess instead of doing it inline. The exception is anything
irreversible or identity-defining (the agent's own persona files, another
agent's persona files, anything with a large and hard-to-undo blast radius):
that stays in the main loop, on the theory that judgement calls shouldn't be
made by something that started the task with no memory of why it matters.

## Compaction and continuity

If your runtime has a context window that eventually fills up and gets
summarised, don't wait for that to happen to you unprompted, mid-task, with no
say in what gets kept. Self-manage it: notice when you're getting close,
finish the unit of work you're in the middle of, write a short handover note
(what's done, what's not, what the next session needs to know that isn't
obvious from the files alone), then compact deliberately. A handover should
distinguish "this works" from "this is durable", code or state that only
exists uncommitted on one machine is not yet safe, and saying so explicitly is
the single most useful thing a handover can do.

## Shared task board (optional)

If you want a lightweight, human-visible view of what every agent is doing
without building a project-management tool, a folder of small files (one per
workstream, a few frontmatter fields: which agent, which column, when it last
changed) rendered by something that just reads the folder gets you most of
the value. Move a card the moment its state changes, don't batch updates, and
don't edit another agent's card out from under it, append your own update
instead.

## This is a living document

Whatever you build here started incomplete and stayed that way. If you spot
something that should be a shared rule but isn't, or a shared rule that's gone
stale, that's normal, fix it rather than working around it silently.
